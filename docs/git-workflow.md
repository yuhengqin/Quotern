# Git 与工作区标准

## 任务隔离

独立修改任务默认采用「一个独立任务 = 一个分支 + 一个 worktree」，以可单独交付和验收的修改目标划分。仅当 `master` 无未提交变更、没有其他正在进行的可写任务，且本任务不需要独立审阅或延后整合时，可直接在 `master` 串行修改和提交，无需额外创建分支与 worktree，以省去单任务开发的合并和清理。纯只读调查或审查无需另建工作区。

- 开始修改前核对仓库、目标分支、工作区绝对路径、起始提交与允许修改范围，并确认是否满足直接修改 `master` 的条件。已有属于同一任务的分支和 worktree 时直接复用，不重复创建；不同独立任务不得共用同一可写工作区。
- 同一任务内的协作者可以共用该任务的工作区，但须明确文件归属，并避免对同一文件或共享状态并发写入；不按子代理数量机械创建 worktree。
- 不满足直接修改 `master` 条件的任务，从明确的已提交基线创建分支和 worktree；未提交变更不会自动带入新工作区，不得为准备工作区覆盖、搬走或混入其他任务的修改。存在任务依赖时明确依赖提交及整合顺序。
- 直接在 `master` 修改期间若需启动并行任务，先完成并提交当前任务，或将其安全迁至独立分支和 worktree，再开始并行修改；不得让不同任务共用未提交变更。
- 各任务分别完成适用验证并审查差异；分支任务再整合其提交，整合后验证受影响的行为。worktree 不消除合并冲突或跨任务的语义冲突。

worktree 隔离代码文件和暂存区，不自动隔离运行资源。启动服务或集成测试前，另行核对端口、配置、数据库、任务队列及其他共享资源的隔离范围，遵守[测试标准](testing.md#检查环境与授权)和[数据与安全标准](data-and-security.md)。

### Worktree 存放位置

优先将 worktree 放在主仓库之外，避免主工作区的搜索、文件监听和备份重复处理其他任务的完整代码副本；项目 `.codex/` 用于配置、Hook 和角色定义。

- Codex 自动管理的 worktree 沿用应用配置的位置，默认位于 `$CODEX_HOME/worktrees/`（通常为 `~/.codex/worktrees/`）；通过应用管理其创建和清理。
- 自行管理的 worktree 优先放在主仓库旁边，按项目和任务组织，例如 `../FacoritesGPT-worktrees/<任务名>/`。本约定不改变上文的分支、基线和任务隔离要求。
- 需要在项目内部存放时，使用 `.worktrees/`，创建前确认已排除 Git 跟踪，并核对代码搜索、文件监听和备份工具的排除规则；不能仅凭 `.gitignore` 推断所有工具均已排除。
- 已有 worktree 继续按所属任务复用，无需为符合目录偏好而迁移。确需迁移时，先核对未提交工作及应用中的任务关联，并遵守下文的[破坏性操作](#破坏性操作)要求。

## 目标明确

所有 Git 操作都要确认当前目录、目标仓库、目标分支和预期影响。禁止把不相关的用户变更混入任务、覆盖未提交工作或借清理之名删除未知文件。

## 破坏性操作

重置、强制覆盖、删除分支、改写历史和大范围移动前，先得到明确授权，记录绝对目标和恢复方式，并确认备份或可恢复点。不能用跳过 Hook、跳过 CI 或修改检查脚本的方式绕过门禁。

## 提交和审阅

提交信息说明目的、范围和验证结果；提交前检查差异、敏感信息、文档同步和测试结果。保持原子提交与清晰的变更历史。
