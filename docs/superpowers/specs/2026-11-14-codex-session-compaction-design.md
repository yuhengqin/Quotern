# Codex 会话压缩用量补齐

用户要求处理已确认的会话用量漏记。案例中独立压缩请求只有 `token_usage_record` 与 `compacted.compaction_response_id`，会话观察层仅接受 `token_count`，因此少记 460,133 Token 和一次请求。

## 范围与约束

- 只补齐会话观察与缓存；不改变任务时长、价格规则或普通累计基线。
- 按响应 ID 配对用量与压缩标记，保留请求发生时的模型、时间、档位与匿名归属；只持久化数值和哈希。
- 已被普通通知覆盖的压缩用量不得重复计入，覆盖证据在范围筛选前处理。
- 保留原普通事件身份，避免旧缓存、归档移动与重扫之间重复计数；fork 继承前缀仍排除。
- 缓存升级自动重读仍存在的日志，原始日志已删除的旧记录继续可读；查询路径不扫描原始日志。
- Node.js 22.13+；依赖与脚本统一使用 `corepack pnpm`，不新增依赖。

## 方案

采用现有观察层内的配对状态及数值事件，不把响应级记录整体替换为普通计量入口。后者会扩大历史事件身份和格式兼容范围；只在 UI 加差额无法修复 CSV、归属与会话查询，且缺少可靠身份。

候选响应保存在采集上下文中，普通请求消费匹配候选；标记与用量齐备时输出稳定哈希身份的压缩事件。普通通知另保留对响应的覆盖哈希，聚合前移除已覆盖压缩事件，兼容标记先到及跨扫描时序。

## 验收

- 独立请求计入一次，五类 Token 拆分、请求数、费用与原始数值一致。
- 双向/跨扫描配对、普通通知覆盖、累计基线、重复事件、分叉回放均不重计。
- 版本 12 缓存升级后自动补齐，删除原日志的旧缓存仍保留。
- 用隔离数据目录复核实际案例 92,651,757 主会话 Token、370 请求；主会话任务时长仍为 9,440 秒。
- Core 回归及 Desktop 的实际分析隔离路径验证通过；不重启或写入其他会话的开发服务数据。
